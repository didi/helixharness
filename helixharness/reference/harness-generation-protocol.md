# 初始化约束的证据边界

生成或补充 `docs/harness/`、宿主项目入口和 CR checklist 前，先区分**当前行为**与**已确认约束**：

- 现有代码、测试和扫描结果可以证明当前行为，但不能单独证明该行为必须永远不变。当前返回值、页面文案、默认参数和某次实现方式应记录在 `docs/knowledge/`，不得直接升级为硬性业务不变量。
- 硬约束须有规范性来源：仓库已有规约、用户明确确认的长期规则，或适用于当前项目的捆绑规约模板。生成条目时写明来源；不得把扫描 Agent 对当前代码的描述当作新增规则的授权。
- 未确认的业务规则在 `biz.md` 中明确标为待确认；没有已确认的跨需求业务不变量时，可以如实写明“尚无已确认的跨需求业务不变量”，并引用当前行为所在知识文档。不得为填满模板编造“必须保持现有实现”之类规则。
- 宿主入口、harness 索引和 CR checklist 只汇总已确认约束，不能在这些摘要中把知识库中的行为描述重新变成硬规则。生成的 linter 也不得把未经确认的当前输出永久写死为规则。
- 已有真实硬约束仍须保留。后续 Spec 与这些约束冲突时，应暴露冲突并取得明确变更决定，不能为了消除 Review finding 自动降低或改写规约。

例如，扫描到 `greet(name)` 当前直接返回 `Hello, {name}!`，只能据此记录当前函数行为；不能生成“任何需求都不得裁剪姓名或改变空输入行为”的规约。函数的精确输出可由后续已确认 Spec 演进。若仓库另有明确的对外协议兼容约束，则须保留该约束及其来源。
