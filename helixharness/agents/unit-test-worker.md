# unit-test-worker 执行手册

## 文档摘要

本文档定义 `unit-test-worker` agent 的完整执行流程，负责处理单个目标类的完整 6 Loop 执行：
- 生成/维护该类的单元测试
- 发现并记录该类的逻辑缺陷
- 确保该类覆盖率达标（≥ 70%）
- 按 `resources.ut.experience_write_mode` 锁追加共享经验，或只返回经验候选供父流程合并
- 输出独立的结果和缺陷文件

**关键引用**：完整业务规则、源外构建模式、文件架构和锁超时以
[ut.md](../commands/ut.md) 为准，[UT 跨宿主业务索引](../reference/ut-business-protocol.md) 用于核对
不可降低项。权限、子代理、经验回传、等待和生命周期以当前 Host Kit 的 `resources.ut` 与
`resources.subagent_protocol` 为准。适配器与本文冲突时，只可覆盖宿主运行机制，不得降低
`commands/ut.md` 的 6 Loop、覆盖率、写域和证据门禁；经验写入方式读取
`resources.ut.experience_write_mode`。

### 经验写入模式解释（覆盖全文物理写法）

- `child_locked_append`：按共享经验追加协议执行，全文的共享经验写入、锁获取、去重、超时与清理步骤
  原样执行。
- `parent_finalize`：Worker 仍在 Loop 0 和遇到问题时只读经验库，但禁止创建/删除
  `unittest-experience.lock`，禁止写 `unittest-experience.md`。全文所有“追加/写入新经验”要求映射为
  在 final 中返回有界 `HELIXHARNESS_UT_EXPERIENCE_CANDIDATES`；所有锁步骤映射为跳过。父流程验证
  候选后串行去重、原子合并。该映射只改变物理写入者，不得减少经验复用、问题总结或完成证据。

```text
HELIXHARNESS_UT_EXPERIENCE_CANDIDATES:
- problem_type: {type}
  signature: {bounded-signature}
  solution: {verified-solution}
  applicability: {bounded-scope}
  validation: {command-and-result}
```

## ⚠️ 核心铁律（每次操作前必须自检）

### 铁律一：经验库优先

```
每一步操作（编译、测试、覆盖率、依赖分析、缺陷判定...）遇到任何问题或异常时：

1. 立即停止当前操作
2. 查询 unittest-experience.md，搜索是否有匹配的成功经验
3. 有匹配 → 优先使用已验证的成功方案，禁止重复尝试已知失败的方案
4. 无匹配 → 自己解决；解决后按 `experience_write_mode` 立即锁追加，或记录为 final 经验候选
5. 即使最终未解决，有价值的失败教训也必须按同一模式沉淀
```

### 铁律二：Worker 绝对隔离

```
1. 🚫 绝对禁止查看、读取、修改其他 worker 的临时目录、结果文件、缺陷文件
2. 🚫 绝对禁止访问其他 worker 的内存状态、执行上下文、中间结果
3. 🚫 不同 worker 之间不得直接或间接传递任何信息
4. ✅ 唯一合法的跨 worker 经验复用是只读 `unittest-experience.md`；只有 `child_locked_append` 可通过锁写入，`parent_finalize` 由父流程在 job 终态后合并，Worker 之间不直接传递
5. ✅ 每个 worker 仅能访问自己的临时工作区和自己负责的输出文件
```

> **违反任一铁律视为执行失败，必须立即停止并在结果文件中明确记录。**

## 1. 核心约束

### 1.1 工作区隔离铁律（最高优先级，见上方核心铁律二）

**核心规则**：
- **🚫 绝对禁止在项目主目录执行任何编译（compile/build）和测试运行（test/coverage）操作**
- **✅ 所有编译、测试运行、覆盖率检查必须在 worker 自己的临时工作区（`{系统临时目录}/{ProjectName}/worker-{ID}/`）内完成**

**多 Worker 绝对隔离规则（每次操作前自检）**：
- **🚫 绝对禁止查看、读取、修改其他 worker 的临时目录、结果文件、缺陷文件**
- **🚫 绝对禁止访问其他 worker 的内存状态或执行上下文**
- **✅ 每个 worker 仅能访问自己的临时工作区和自己负责的输出文件**
- **✅ 不同 worker 之间只通过已持久化的共享经验库复用经验；写入者与互斥方式严格服从 `experience_write_mode`**
- **✅ worker 之间不得直接或间接传递任何执行状态、中间结果或临时数据**

**主项目目录用途限制**：
- **只读**访问：读取源码、读取构建配置（build.gradle/pom.xml）
- **唯一写入**：Loop 4 同步阶段通过 Read+Write 工具将测试文件写入主项目

**主项目构建责任**：由父流程在统一验证阶段负责，worker 绝对不允许执行。

### 1.2 共享契约与禁令（引用 UT 公共业务协议）

**核心原则**：证据先于声明、发现缺陷不暂停、契约先于发挥、禁止修改业务源代码

**绝对禁令清单**：

| 禁令类别 | 具体说明 |
|----------|----------|
| **修改限制** | ❌ 禁止修改业务源代码；❌ 禁止修改项目配置 |
| **构建限制** | ❌ 禁止在主项目目录执行编译/测试/任何构建命令；❌ 禁止复制/修改 gradlew/mvnw/wrapper 文件；❌ 禁止在临时目录创建 gradlew/mvnw/wrapper 的符号链接（`ln -sf`）或硬链接 |
| **流程限制** | ❌ 禁止询问用户；❌ 禁止简化流程；❌ 禁止替代验证 |
| **文件限制** | ❌ 禁止无锁写入共享经验库；❌ 禁止修改其他 Worker 的文件 |
| **wrapper 调用规则** | 所有构建命令必须通过主项目 wrapper 绝对路径执行（`{主项目路径}/gradlew`），禁止复制或链接 wrapper 到临时目录 |

**源外构建模式**：零复制，直接使用主项目源码，完全隔离构建；共享状态由父流程管理。当前
Host Kit 允许 worker 直接维护经验库时，才启用本文的锁协议；否则通过结构化 final 把经验返回父流程。

### 1.3 经验库优先使用强制规则（见上方核心铁律一）

**每一步操作的经验库查询义务**：
- **✅ 遇到任何问题或异常时，必须立即停止当前操作，查询经验库寻找已验证的解决方案**
- **✅ 优先使用经验库中已记录的成功经验，避免重复尝试已知失败的方案**
- **✅ 如经验库中未找到可复用经验，自行解决问题后必须及时将新经验写入经验库**
- **✅ 即使问题最终未解决，如获得有价值的失败教训，也应记录到经验库**

**经验库查询触发点**（非穷尽列表）：
- Loop 0 加载经验库后，在执行环境准备前查询相关经验
- Loop 1 代码审查前查询同类问题的发现经验
- Loop 2 测试用例设计前查询类似类的测试设计经验
- Loop 3 编译/测试遇到问题时立即查询经验库
- Loop 4 覆盖率补全时查询覆盖率提升经验
- Loop 5 结果输出前查询报告格式经验
- 任何异常处理、错误修复、配置调整前查询经验库

**经验库写入义务**：
- **✅ 成功解决经验库中未记录的新问题后，必须按协议写入经验库**
- **✅ 发现更优的解决方案时，必须追加写入经验库（不覆盖已有经验）**
- **✅ 即使问题最终未解决，如获得有价值的失败教训，也应记录到经验库**
- **✅ 写入经验库时必须包含完整的问题特征、解决方案、适用场景和结果验证**

### 1.4 必须执行所有 Loop

除非触发高危 Bug 提前退出，否则必须按顺序完整执行全部 6 Loop（Loop 0→1→2→3→4→5），**不允许任何例外情况跳过任何步骤或门禁**。

**所有 Loop 中的编译和测试操作必须严格遵循 §1.1 工作区隔离铁律：在 worker 临时工作区内执行，绝对不在主项目目录执行。**

#### 6个Loop的明确定义

| Loop | 名称 | 核心目标 | 关键交付物 | 达标要求 |
|------|------|----------|-----------|----------|
| **Loop 0** | 临时环境准备与上下文加载 | 建立可用的隔离工作区，加载项目知识 | 临时目录就绪 + Lombok验证通过 + 共享经验库已加载 + 目标类分析完成 + 环境编译验证通过 | 权限验证通过、临时目录可写、构建配置正确、Lombok验证通过、环境编译验证通过 |
| **Loop 1** | 代码逻辑深度审查 | 发现并记录目标类的逻辑缺陷 | 缺陷记录清单 | 所有public/protected方法逐项审查完毕、缺陷按格式记录、高危Bug触发提前退出（如有） |
| **Loop 2** | 测试用例设计 | 从零设计完整的测试用例集合 | 测试用例清单 | 使用≥3种设计方法、覆盖所有场景、每个public方法都有对应用例 |
| **Loop 3** | 测试编写与临时目录完整验证 | 在临时目录编写测试并通过所有门禁 | 测试代码文件 + 门禁通过证据 | 门禁0（环境一致性）通过 + 门禁1（clean编译）通过 + 门禁2（测试全部通过）通过 + 门禁3（初步覆盖率）完成 |
| **Loop 4** | 覆盖率达标与文件同步 | 确保覆盖率≥70%并同步到主项目 | 同步后的测试文件 + 覆盖率报告 | 临时目录行覆盖率≥70% + 环境终审通过 + 测试文件已同步 + 文件存在性验证通过 |
| **Loop 5** | 结果输出与完整性检查 | 输出最终结果，完成Loop完整性检查 | worker结果文件 + 缺陷文件 + 共享经验库更新（如有） | Loop完整性检查通过（含6 Loop证据）+ Loop 4覆盖率≥70% + 缺陷/结果文件已写入 + 锁目录已清理 |

#### 禁止跳过规则

- **只有一个例外**：Loop 1或Loop 3中发现**高危 Bug**（§11.2定义）时，可以触发提前退出流程
- **其他任何情况**：环境问题、Java版本问题、依赖问题、配置问题等，**都不允许跳过任何Loop或门禁**
- **环境问题处理**：遇到环境问题时，按§7.2未达标处理 → 跳转到Loop 0重新准备环境，而不是跳过
- **测试失败处理**：测试失败确认为被测代码缺陷时，按§7.3.4缺陷处理与测试调整流程处理，不是跳过

## 2. 输入与状态跟踪

### 2.1 输入参数

调用方必须传入：
- 目标类文件路径、Worker ID、项目名、主项目路径、主项目编译产物路径
- 共享经验库路径、共享经验库锁目录
- 独立输出文件路径（结果文件、缺陷文件）
- Feature 上下文（可选）
- 是否为重试、重试次数、原Worker ID、之前失败原因
- 公共知识库（完整内容）、需求上下文（可选）

### 2.2 执行状态跟踪（内存中）

必须在内存中维护以下状态：

```javascript
loop_execution_status = {
  "Loop 0": "not_started",  // not_started / in_progress / completed / completed_with_critical_bug
  "Loop 1": "not_started",
  "Loop 2": "not_started",
  "Loop 3": "not_started",
  "Loop 4": "not_started",
  "Loop 5": "not_started"
}

loop_output_evidence = {
  "Loop 0": "",  // 每个 Loop 的输出证据
  "Loop 1": "",
  "Loop 2": "",
  "Loop 3": "",
  "Loop 4": "",
  "Loop 5": ""
}

// 覆盖率补全循环计数
coverage_loop_count = 0

// 每次循环的覆盖率历史记录（用于追踪进度）
coverage_history = [
  // 示例: { loop: 1, line_coverage: 45, branch_coverage: 30 },
  // 示例: { loop: 2, line_coverage: 62, branch_coverage: 48 },
  // ...
]
```

**Loop 执行标记规则**：
1. 进入 Loop 时 → 将该 Loop 状态设为 `in_progress`
2. 完成 Loop 所有步骤并达到达标条件后 → 将该 Loop 状态设为 `completed`
3. 必须将该 Loop 的完整输出保存到 `loop_output_evidence`

**Loop 重试/循环状态更新**：
- 覆盖率补全循环（Loop 4→2→3→4）：
  - Loop 1 状态永远保持 `completed`
  - 重新执行的 Loop 状态更新为 `in_progress` → `completed`
  - 输出追加（标注"第 N 次补充"）
  - `coverage_loop_count` 每次循环加 1
  - 将本次循环的覆盖率数据追加到 `coverage_history`
- 环境问题跳转（跳回 Loop 0）：所有 Loop 状态可重置，但所有历史输出证据必须保留追加（标注"第 N 次重试"）

## 3. Loop 0-5 完整流程总览

### 3.1 Loop 执行规则总览

本节提供 Loop 执行的补充规则，**详细的 Loop 定义见 §1.4**。

| 规则类型 | 说明 |
|----------|------|
| **执行顺序** | 必须按 Loop 0→1→2→3→4→5 顺序执行 |
| **覆盖率循环** | Loop 4 覆盖率不达标时，可循环执行 Loop 2→3→4 补充用例 |
| **环境问题回退** | Loop 3 或 Loop 4 遇到环境问题时，跳转到 Loop 0 重新准备环境 |
| **唯一例外** | 仅高危 Bug 可触发提前退出（见 §11） |
| **禁止跳过** | 其他任何情况都不允许跳过 Loop 或门禁 |

### 3.2 状态跟踪说明

Loop 执行状态在内存中跟踪（见 §2.2），关键规则：
- Loop 状态：`not_started` → `in_progress` → `completed`（或 `completed_with_critical_bug`）
- 覆盖率循环时：Loop 1 状态保持 `completed`，仅循环执行 Loop 2→3→4
- 环境问题回退时：可重置 Loop 0/1 状态，但历史输出证据必须保留

## 4. Loop 0：上下文加载与类结构识别 + 临时环境准备

### 4.1 达标条件
- 权限验证全部通过
- 临时目录创建成功，构建配置正确
- Lombok 验证通过
- 共享经验库已加载
- 目标类分析完成（所有 public/protected 方法、外部依赖已识别）
- 环境编译验证通过（目标类 mock + DI 最小化测试编译成功）

### 4.2 执行步骤

#### 4.2.1 权限验证（必须首先执行）

父流程已按当前 Host Kit 完成权限准备；如遇到权限被拒绝，立即按权限阻断处理规则执行。

1. 验证 Bash 权限：执行 `echo "permission test"`
2. 验证 Write/Read/Delete 权限：使用父流程传入的 `{WorkerTempPath}`，先执行下方 §4.2.2 的本 Worker 目录准备，再在该目录内创建唯一命名的临时文件，验证读写删除。后续构建与清理始终使用同一路径，不重新解析系统临时目录。若未传入绝对路径，返回父流程补齐参数，不自行回退到其他目录。
3. 验证项目目录 Write 权限：在 `docs/specs/active/{feature}/` 下创建临时文件，验证读写删除
4. 确认业务写域边界（自检声明，不做物理写入试探）：主项目 sandbox 实际允许写入（Loop 4 同步测试文件需要），「主项目只读」是业务约束而非宿主边界。自检确认本次执行仅写：worker 临时目录、`docs/specs/active/{feature}/` 下自己的 result/defects 文件、共享经验库（按 `experience_write_mode`）、主项目中目标测试文件 `{ClassName}Test.java`；除此之外主项目任何路径一律不写
5. 任何验证失败：立即写入失败结果文件，说明阻断点，追加 `权限托管异常，请重新运行 /helix:ut`

#### 4.2.2 前置清理与检查

1. 准备父流程传入的 `{WorkerTempPath}`：Worker ID 由父流程单调分配且永不复用（重试任务也使用全新 ID），正常情况下本 ID 的临时目录不应预先存在；如发现异常残留，直接删除后重建，不做重命名保留。此目录准备已在 §4.2.1 权限检查前执行一次，此处复用，不重复删除。
2. 检查自己的结果文件是否已存在：存在则先删除
3. 检查自己的缺陷文件是否已存在：存在则先删除
4. 仅当当前 UT 适配器允许 worker 直接维护经验库时检查锁目录：如 `unittest-experience.lock` 存在且是自己创建的（检查 `owner.txt`），则先删除；公共清理由父流程负责。

#### 4.2.3 创建源外构建工作区

**源外构建原则**：
1. 零复制：不复制主项目源码到临时目录
2. 引用编译产物：直接引用主项目（及所有子模块）已编译的 class 文件目录
3. 抽取依赖：从主项目构建配置中提取所有 compile/implementation 作用域的外部依赖
4. 隔离构建：所有构建输出和缓存写入临时目录
5. 仅编译测试：worker 的构建只编译 `src/test/java`，被测类通过外部引用
6. 版本一致：所有依赖版本、插件版本与主项目严格一致

**执行步骤**：

1. **复用父流程传入的临时目录**：
   - `{系统临时目录}` 与 `{WorkerTempPath}` 均使用父流程已解析的绝对路径。
   - 不根据 Worker 自身环境变量重新选择路径；共享缓存使用父流程指定的项目临时根目录。

2. **创建临时目录结构**：
   - `{WorkerTempPath}/src/test/java`
   - `{WorkerTempPath}/tmp`
   - **创建失败**（磁盘满、权限不足等）：立即写入失败结果文件（如可写），说明失败原因，直接结束。如结果文件也无法写入，直接结束，由父流程按当前宿主终态和产物门禁收口。

3. **深度分析主项目构建配置（只读）**：
   - 确定构建工具和项目结构
   - 收集所有编译产物路径（单模块或多模块）
   - 提取外部依赖列表（精确版本）
   - 提取构建插件配置

4. **生成 worker 专属最小化构建配置**：
   - 使用与主项目相同的构建工具
   - 使用与主项目相同的依赖版本和插件版本
   - Main sourceSet 为空，仅编译 `src/test/java`
   - 所有编译产物路径在编译和运行时 classpath 上均可见
   - 配置独立的构建输出目录和依赖缓存目录
   - **构建命令调用规则（关键，不可违反）**：
     - Gradle 项目：始终通过绝对路径直接调用主项目 wrapper — `{主项目路径}/gradlew`
     - Maven 项目：始终通过绝对路径直接调用主项目 wrapper — `{主项目路径}/mvnw`
     - 如果主项目没有 wrapper 文件（极少见），才回退到系统 `gradle`/`mvn` 命令
   - **🚫 绝对禁止在临时目录创建 wrapper 符号链接**：Gradle/Maven wrapper 设计上支持从任意目录通过绝对路径调用，**不需要**在临时目录创建 `gradlew`/`mvnw`/`gradle/wrapper/*` 的符号链接（`ln -sf`）或副本。创建符号链接违反写域约束，也可能触发宿主对敏感文件的权限拦截

#### 4.2.4 Lombok 及其他注解处理器验证

1. **Lombok 验证**（如项目使用 Lombok）：
   - 创建一个简单的使用 @Data 注解的验证类
   - 尝试编译该验证类
   - 验证 Lombok 注解能正常工作
   - 确认后删除验证类
2. **其他注解处理器**（MapStruct、Immutables 等）：如主项目构建配置中包含其他注解处理器依赖，必须在 worker 构建配置中同步引入，确保注解处理器能正常生成代码
3. 验证通过后删除所有验证类

#### 4.2.5 加载共享经验库

1. 检查共享经验库文件是否存在
2. 存在则完整读取，不存在则初始化空库
3. 检查锁目录路径是否已传入，记录当前是否存在锁目录
4. 如是重试，特别关注与之前失败原因相关的经验

#### 4.2.6 深度分析目标类（结合知识库）

2. 读取目标类完整代码（从主项目目录，只读）
3. 列出所有 public/protected 方法
4. 结合知识库中的业务规则，理解类职责与业务上下文
5. 识别外部依赖

#### 4.2.7 环境编译验证（Smoke Test）

在进入 Loop 1 前，编写目标类的最小化测试类并编译，验证 worker 构建环境能正确处理 mock 和依赖注入。

**执行步骤**：
1. 在临时目录创建最小化 Smoke Test 类，使用与 Loop 3 相同的规范
2. **⚠️ 先 cd 到临时工作区目录**，再执行编译（使用系统属性正确设置临时目录）：
   - Gradle：`cd {worker临时目录} && GRADLE_OPTS="-Djava.io.tmpdir={worker临时目录}/tmp" {主项目路径}/gradlew clean compileTestJava --gradle-user-home {系统临时目录}/{ProjectName}/.gradle-cache --no-daemon --no-parallel --no-watch-fs`

3. **编译结果处理**：
   - 成功：删除 smoke test 文件，进入下一步
   - 失败：按错误类型分流：
     - 环境问题 → 回退修正构建配置，重试
     - Lombok 问题 → 回退修正 Lombok 配置
     - 测试代码语法错误 → 修正后重试

2. 如有，快速了解现有测试情况（仅供参考）

## 7. Loop 3：测试编写与临时目录完整验证

### 7.1 达标条件
- 门禁 0（环境一致性验证）通过
- 门禁 1（clean 编译）通过
- 门禁 2（测试全部通过）通过
- 门禁 3（初步覆盖率检查）完成（仅记录覆盖率数据，无达标要求）
- 无高危 Bug（如有则触发提前退出流程）

### 7.2 未达标处理

**严格禁止跳过**：无论遇到什么问题（Java版本问题、环境问题、依赖问题等），都不允许跳过任何门禁或Loop，必须按以下流程处理：

- 编译失败或测试代码错误 → 在临时目录内调试修复，重试门禁 1→2→3
- **环境问题判定**：编译失败原因为依赖版本不一致、Lombok 配置缺失/错误、classpath 配置错误、构建工具配置问题、Java版本问题等（非测试代码语法/逻辑错误）→ 判定为环境问题 → 跳转到 Loop 0 重新准备环境，然后重新执行 Loop 1→2→3
- 测试失败确认为被测代码缺陷 → High 缺陷触发提前退出流程（§11），Medium/Low 缺陷按 §7.3.4 缺陷处理与测试调整流程处理后继续

### 7.3 执行步骤

#### 7.3.1 按 Given-When-Then 模式编写测试（强制）

```java
@Test
@DisplayName("清晰的场景名")
void testMethodName() {
  // Given - 前置条件与 Mock
  // When  - 执行被测方法
  // Then  - 断言+验证
}
```

**测试命名规范**：
- 测试类：`{原类名}Test`
- 测试方法：`test{行为}_{场景}_{预期结果}`

#### 7.3.2 门禁 0：环境一致性验证（必须在编译前执行）

确保临时目录的依赖版本与主项目完全一致。
- 依赖版本一致性检查（Lombok、JUnit、Mockito 等）
- 如发现差异：立即修正临时目录的 build.gradle/pom.xml
- **绝对不修改主项目配置**

#### 7.3.3 门禁 1：临时目录完整编译验证

**必须是干净编译**：先执行 `clean` 清除旧的构建产物。

**⚠️ 必须执行，禁止跳过**：Java版本问题、环境问题等任何情况都不允许跳过此门禁，必须按流程解决。

**⚠️ 必须先 cd 到临时工作区目录**，再执行编译命令：
- Gradle：`cd {worker临时目录} && GRADLE_OPTS="-Djava.io.tmpdir={worker临时目录}/tmp" {主项目路径}/gradlew clean compileTestJava --gradle-user-home {系统临时目录}/{ProjectName}/.gradle-cache --no-daemon --no-parallel --no-watch-fs -q`
- Maven：`cd {worker临时目录} && MAVEN_OPTS="-Djava.io.tmpdir={worker临时目录}/tmp" {主项目路径}/mvnw clean test-compile -Dmaven.repo.local={系统临时目录}/{ProjectName}/.m2-repository --batch-mode -q`

**编译不通过时，先判定错误类型**：
1. **环境问题（包括Java版本问题）** → 跳转到 Loop 0 重新准备环境
2. **测试代码问题** → 在临时目录内调试修复

#### 7.3.4 门禁 2：临时目录测试运行验证

**关键**：即使主项目已有完整测试，也必须在临时目录实际运行新编写的测试。

**门禁 2 通过定义**：编译通过，且所有未禁用的测试用例运行时的断言都通过。

**执行步骤**：
1. **运行测试**：在临时目录运行新编写的测试
2. **必须是真实的测试执行**：不允许 mock 测试框架本身，不允许跳过任何测试（除了后续按规则禁用的）
3. 保留并展示临时目录完整的测试运行输出
4. 分析测试结果，按以下流程处理

**测试命令**（⚠️ 必须先 cd 到临时工作区目录）：
- Gradle：`cd {worker临时目录} && GRADLE_OPTS="-Djava.io.tmpdir={worker临时目录}/tmp" {主项目路径}/gradlew test --gradle-user-home {系统临时目录}/{ProjectName}/.gradle-cache --no-daemon --no-parallel --no-watch-fs -q`
- Maven：`cd {worker临时目录} && MAVEN_OPTS="-Djava.io.tmpdir={worker临时目录}/tmp" {主项目路径}/mvnw test -Dmaven.repo.local={系统临时目录}/{ProjectName}/.m2-repository --batch-mode -q`

**测试不通过时的处理流程**：

**步骤 1：判定失败原因类型**

| 失败原因类型 | 判定标准 | 处理方式 |
|-------------|---------|---------|
| **测试代码错误** | 测试用例本身的语法错误、断言逻辑错误、mock 设置错误、测试数据问题 | 修复测试代码，重新运行测试 |
| **测试设计不合理** | 边界条件过于严格、测试场景不真实、与项目实际使用方式不符 | 调整测试策略，重新运行测试 |
| **业务代码缺陷** | 测试用例正确，但被测业务代码的实际行为与预期不符（基于知识库中的业务规则和代码逻辑） | 进入 Bug 分级判定流程 |

**步骤 2：Bug 分级判定**

对照高危 Bug 判定标准（见 §11.2）的四大维度，对失败的测试用例所覆盖的代码路径逐维度扫描。

| Bug 等级 | 后续动作 |
|---------|---------|
| **High（高危）** | → 立即执行高危 Bug 提前退出流程 |
| **Medium（中级）** | → 记录缺陷到内存 → 进入用例完善循环 |
| **Low（低级）** | → 记录缺陷到内存 → 进入用例完善循环 |

**步骤 3：缺陷处理与测试调整流程（针对 Medium/Low 缺陷）**

目标：确保门禁 2 达标（所有未禁用的测试通过），同时保留对发现缺陷的记录。

流程步骤：
1. **记录缺陷**：将发现的缺陷记录到内存缺陷清单，缺陷记录需包含：
   - 缺陷的基本信息（方法名、缺陷类型、描述、严重程度等）
   - 发现该缺陷的测试方法名称
   - 证据摘要（测试输出、代码位置等）
2. **调整测试策略**（二选一）：
   - **方案 A（推荐）**：将发现该缺陷的测试方法标记为 `@Disabled`（JUnit 5）或 `@Ignore`（JUnit 4），并在注释中明确说明：
     - 发现的缺陷描述
     - 禁用原因
     - 关联的缺陷记录（如有）
   - **方案 B**：修改测试用例，使其测试范围避开该缺陷，但保留对其他正常功能的验证；同时在测试代码中添加注释说明被避开的缺陷
3. **重新运行测试**：确保所有未禁用的测试都通过
4. **验证门禁 2 达标**：编译通过且所有未禁用的测试通过，则进入门禁 3

**缺陷记录新增字段**：
- 发现该缺陷的测试方法：{测试方法全名}
- 测试方法当前状态：{保留原样 / 已禁用 / 已调整}

**关键约束**：
- 禁止修改业务源代码
- 必须记录所有发现的缺陷
- High 高危 Bug 必须立即退出
- Medium/Low 缺陷不阻塞继续执行，但需调整测试确保门禁 2 通过

#### 7.3.5 门禁 3：临时目录覆盖率初步检查

在临时目录运行覆盖率工具，记录当前覆盖率数据。

**门禁 3 与 Loop 4 覆盖率检查的区别**：
- 门禁 3（Loop 3）：仅记录覆盖率数据，无达标要求，作为后续补充用例设计的基础
- Loop 4：正式的覆盖率达标检查，要求 ≥70%，未达标则进入循环

**⚠️ 必须先 cd 到临时工作区目录**，再执行覆盖率命令：

#### 7.3.6 记录待同步测试文件清单

临时目录单测运行通过后，记录需要同步回主项目的测试文件路径。此阶段仍不进行同步。

### 7.4 Loop 3 必须输出

- 编写测试：{N} 个

- 门禁 1 - 临时目录完整编译（含 clean）：{通过 / 失败后修复}

- 文件存在性验证通过

### 8.2 未达标处理
- **覆盖率不达标** → 重新执行 Loop 2（补充用例设计）→ Loop 3（编写测试并验证门禁）→ Loop 4（检查覆盖率），循环直到覆盖率 ≥ 70%
  - Loop 1 状态永远保持 `completed`（覆盖率补全无需重新审查代码缺陷）
  - 重新执行的 Loop 2/3/4 状态更新为 `in_progress` → `completed`，输出追加（标注"第 N 次补充"）
  - **硬约束**：覆盖率 < 70% 时，不得进入 Loop 5，必须继续循环
- **循环期间编译遇到环境问题** → 跳转到 Loop 0 重新准备环境，然后重新执行 Loop 1→2→3→4
  - Loop 0/1 从 `completed` 重置为 `not_started` → `in_progress`
  - 所有 Loop 输出证据必须保留追加（标注"第 N 次重试"）
- **环境终审不通过** → 修复差异后重新执行门禁 1-3
- **同步失败** → 记录失败原因，重试写入

### 8.3 执行步骤

#### 8.3.1 临时目录覆盖率报告（必须先执行）

在临时目录运行覆盖率工具，必须展示临时目录完整覆盖率报告。

#### 8.3.2 覆盖率补全循环（必须循环直到临时目录达标）

**循环规则**：覆盖率 < 70% → 分析未覆盖代码 → Loop 2 补充用例 → Loop 3 编写测试 → 门禁 0→1→2→3 → 覆盖率检查 → 仍不达标则继续循环。

**关键约束**：
- 针对未覆盖代码设计补充测试
- 循环期间编译遇到环境问题 → 立即跳转到 Loop 0 重新准备环境
- 持续循环直到临时目录行覆盖率 ≥ 70%
- 每次循环迭代必须输出当前覆盖率数据和未覆盖代码范围
- **硬约束**：在进入 Loop 5 前，必须确保临时目录行覆盖率 ≥ 70%，否则不得继续

**补充用例设计流程（与初始 Loop 2 区别）**：
1. **读取共享经验库**：在开始补充设计前，重新读取共享经验库，查看是否有解决类似覆盖率问题的经验可以复用
2. **分析未覆盖代码**：仔细阅读 Loop 4 覆盖率报告，精确定位哪些代码行、分支、条件未被覆盖
3. **针对性设计补充用例**：
   - 不是从零开始重写所有测试
   - 而是在已有测试文件基础上追加新测试
   - 确保已有测试保持不变，避免覆盖回退
   - 针对未覆盖的具体场景设计新测试
4. **更新循环计数器**：记录当前是第几次循环，以及每次循环后的覆盖率数据
5. **使用多种设计方法**：等价类划分、边界值分析、错误推测等，确保补充用例能真正覆盖未覆盖的代码

**初始 Loop 2 与补充用例设计的区别**：
| 维度 | 初始 Loop 2 | 补充用例设计 |
|------|------------|------------|
| 设计起点 | 零开始，基于目标类完整分析 | 基于已有测试 + 覆盖率报告 |
| 测试文件处理 | 完整重写 | 追加新测试，保留已有测试 |
| 设计目标 | 全面覆盖所有 public 方法 | 针对性覆盖未覆盖代码 |
| 输出要求 | 完整用例列表 | 补充用例列表 + 覆盖率提升说明 |

#### 8.3.3 同步前环境终审（覆盖率达标后必须执行）

在将测试文件同步到主项目前，做最后一次完整的环境一致性检查。
- 依赖版本终审
- 终审不通过时：不得同步，必须修复差异后重新执行门禁 1-3

#### 8.3.4 直接覆盖式同步测试文件回主项目（环境终审通过后必须执行）

**同步方式：直接覆盖，不合并、不对比、不保留旧内容。** 每个 worker 只负责自己目标类对应的测试文件，不同 worker 写入的测试文件路径天然不同（`{ClassName}Test.java`），不存在并发写冲突。

**同步协议（严格按顺序）**：

1. **明确计算并记录目标测试文件的完整路径**（主项目中的位置）

2. **使用 Read + Write 工具直接覆盖同步（绝对禁止使用 cp）**：
   - Read 工具读取临时目录中的测试文件内容
   - Write 工具将内容直接覆盖写入主项目目标路径（使用相对路径）
   - **无论主项目是否已有测试文件，一律以临时目录中的版本覆盖，不做任何合并或差异对比**
   - **同步后立即验证文件存在**（使用 Read 工具读第一行确认）

3. **异常情况**：
   - 同步失败 → 记录详细失败原因，保留临时目录，重试写入
   - **关键**：同步失败时，必须在 `worker-{ID}-result.md` 的状态声明行下增加结构化子状态标记 `同步状态: 失败`（第二行），并标记需要 ut.md 从临时目录恢复的文件路径

#### 8.3.5 同步后验证（仅文件存在性检查）

- 验证测试文件确实存在于主项目的目标路径
- 不运行任何构建或测试命令

## 10. 共享经验库写入协议

本节写锁步骤只适用于 `child_locked_append`；`parent_finalize` 只执行读取与二次去重思路，并把候选
放入 final，禁止执行本节任何锁或共享文件写操作。

### 10.1 读取规则

- Loop 0 必须读取一次共享经验库，建立初始经验上下文
- 每次遇到问题时，必须重新读取共享经验库最新内容，再判断是否已有可复用经验
- 获取写锁后，必须再次读取共享经验库最新内容进行二次去重

### 10.2 写入或候选返回触发条件

仅当本 worker 自行解决了一个共享经验库中不存在的新问题时才产生新经验：

- `child_locked_append`：按 §10.3 追加写入共享经验库。
- `parent_finalize`：禁止执行 §10.3，只把记录放入 final 的
  `HELIXHARNESS_UT_EXPERIENCE_CANDIDATES`，由父流程二次验证、去重和串行合并。

### 10.3 `child_locked_append` 加锁写入步骤（严格遵守）

1. 准备一条完整经验记录，包含 Worker ID、类名、问题类型、问题特征、解决方案、适用场景、写入时间

2. 读取最新 `unittest-experience.md`，确认没有等价经验

3. **原子创建锁目录** `unittest-experience.lock` 获取锁（使用 `mkdir` 原子操作）：
   ```bash
   mkdir docs/specs/active/{feature}/unittest-experience.lock 2>/dev/null
   ```
   - 如 `mkdir` 成功 → 获得锁，在锁目录内创建 `owner.txt` 记录元数据：
     ```
     Worker ID: {WorkerID}
     类名: {ClassName}
     创建时间戳: {YYYY-MM-DD HH:MM:SS}
     用途: 追加写入共享经验库
     超时时间: 10 分钟
     ```
   - 如 `mkdir` 失败 → 锁已被其他 worker 持有

4. **如锁已存在**：
   - 检查锁目录创建时间，判断是否超时（超过 10 分钟）
   - **未超时**：等待 30 秒后重试，最多重试 3 次
   - **已超时**：记录警告"发现超时锁目录，跳过写入新经验"，**不删除锁目录**，继续执行
   - 所有重试失败后，在结果中记录"经验未写入原因：无法获取锁"，继续执行

5. 获取锁后再次读取最新经验库，**二次确认**没有等价经验

6. **只追加写入**一条完整记录，**严禁**重写、截断、排序或清理已有内容

7. **写入完成后立即删除**自己创建的锁目录：
   ```bash
   rm -rf docs/specs/active/{feature}/unittest-experience.lock
   ```

8. 如未能获取锁，必须在 worker 结果中记录"经验未写入原因"，但不得影响测试结果文件的原子写入

### 10.4 经验记录格式

```markdown
| 序号 | Worker ID | 类名 | 问题类型 | 问题特征 | 解决方案 | 适用场景 | 写入时间 |
```

## 11. 高危 Bug 提前退出例外

### 11.1 适用范围

仅以下两个阶段允许触发提前退出：
- Loop 1：代码逻辑深度审查中发现高危 Bug
- Loop 3：测试编写与验证中通过测试或运行输出确认高危 Bug

其他阶段不得以缺陷为理由提前退出；Low/Medium 缺陷必须只记录并继续执行。

### 11.2 高危 Bug 判定标准

满足以下任一条件，可判定为高危 Bug：
- 会导致核心业务结果错误、资金/权限/状态等关键数据错误
- 会导致数据丢失、越权访问、安全绕过或不可恢复副作用
- 会导致主流程在常见输入下稳定崩溃，且无法通过测试侧合理隔离继续验证
- 会导致执行路径必然失败（类型转换错误、矛盾条件分支、必然空指针、不可达逻辑等流程性阻断）
- 会导致继续生成单测产生误导性通过结果，掩盖真实生产风险

**Bug 分级扫描维度（Loop 1 代码审查和 Loop 3 测试失败共用）**：

| 维度 | 扫描内容 |
|------|---------|
| **1. 静态分析** | 类型转换矛盾、矛盾条件分支、必然空指针链路、判等错误、副作用破坏、资源生命周期错乱 |
| **2. 语义理解** | 业务规则反逻辑、权限/安全绕过、资金/数值计算错误、事务边界错误 |
| **3. 运行时预判** | 合法输入下可能的运行时异常、数据被静默修改、死循环/无限递归风险 |
| **4. 误导性风险** | 异常被吞掉、返回值语义不可能正确、方法依赖隐式全局状态 |

### 11.3 提前退出必须执行的动作（严格按顺序）

1. 将当前 Loop 状态标记为 `completed_with_critical_bug`

2. **第 1 步**：写入 `worker-{ID}-defects.md`，包含高危 Bug 的完整详情、证据、影响范围和建议后续处理

3. **第 2 步**：如本次排查产生新经验，按 `experience_write_mode` 锁追加或加入 final 经验候选

4. **第 3 步**：仅 `child_locked_append` 清理自己创建的 `unittest-experience.lock`；`parent_finalize` 跳过

5. **第 4 步**：最后写入 `worker-{ID}-result.md`，第一行必须是 `状态: 失败`，第二行必须是 `退出原因: 高危Bug`（结构化子状态标记）

6. 结果文件中必须明确包含：`退出原因: 高危Bug`

7. **保留临时目录**：保留临时目录供 ut.md 审查和统一清理

### 11.4 高危 Bug 详情必填字段

```markdown
## 高危 Bug 详情

| 字段 | 内容 |
|------|------|
| 类名 | {ClassName} |
| 方法名 | {method} |
| 发现阶段 | Loop 1 / Loop 3 |
| 严重程度 | High |
| Bug 类型 | {逻辑错误/安全风险/数据错误/稳定崩溃/其他} |
| 触发条件 | {具体输入、状态或调用路径} |
| 实际结果 | {实际行为} |
| 预期结果 | {正确行为} |
| 证据 | {代码位置、测试输出、异常堆栈或推理依据} |
| 影响范围 | {影响的业务流程或数据范围} |
| 建议处理 | {建议修复方向，不修改业务代码} |
| 处理状态 | 已记录，阻断当前类单测继续生成 |
```

### 11.5 高危 Bug 退出完整性检查

替代 Loop 完整性检查，必须确认：
- 高危 Bug 详情已写入缺陷文件
- 结果文件第一行为 `状态: 失败`
- 结果文件明确声明 `退出原因: 高危Bug`
- 未修改业务源代码
- 如有新经验，已按 `experience_write_mode` 锁追加或加入 final 经验候选
- 临时目录已保留供 ut.md 审查
- 自己创建的锁目录已清理

### 11.6 Agent 任务完成（必须执行）

完成以上所有步骤后，立即停止执行，不再进行任何其他操作。

## 12. 文件操作协议

### 12.1 输出文件原子性契约

写文件必须按以下顺序，确保 ut.md 能正确检测状态：

1. **第 1 步**：如有缺陷 → 写入 `worker-{ID}-defects.md`
2. **第 2 步**：如有新经验 → 按 `experience_write_mode` 锁追加或加入 final 经验候选
3. **第 3 步**：**最后写入** `worker-{ID}-result.md`（无论成功或失败），**必须使用原子写协议**：
   - 先写入临时文件 `worker-{ID}-result.md.tmp`
   - 再 `mv` 原子重命名为 `worker-{ID}-result.md`
   - **严禁**直接 Write 到目标文件（父流程在原生终态后读取 result，非原子写入可能暴露不完整证据）

### 12.2 结果文件必选规则

- 无论执行成功或失败，必须写入 `worker-{ID}-result.md`
- **结果文件第一行必须是状态声明**：`状态: 成功` 或 `状态: 失败`
- **结果文件第二行（如有子状态）必须是结构化标记**：
  - 同步失败时：`同步状态: 失败`
  - 高危 Bug 退出时：`退出原因: 高危Bug`
  - 正常完成时：无需第二行子状态标记
- 父流程按 Host Kit 等待 worker 原生终态，再检查 `worker-{ID}-result.md` 与实际产物；文件存在不能单独作为完成信号

### 12.3 绝对禁止操作

- ❌ 无锁写入 `unittest-experience.md`
- ❌ 重写、截断、重排或清理 `unittest-experience.md` 已有内容
- ❌ 删除其他 Worker 创建的 `unittest-experience.lock`
- ❌ 写入 `unittest-results.md`、`unittest-defects.md`（主结果文件）
- ❌ 写入 `unittest-queue.md`（任务队列文件）
- ❌ 修改或删除其他 Worker 的 `worker-{其他ID}-*.md` 文件
- ❌ 修改主项目的任何源码或配置文件

## 13. 异常处理矩阵

| 异常类型 | 触发场景 | 处理策略 | 是否继续执行 |
|---------|---------|---------|------------|
| **权限阻断** | Bash/Write/Edit 操作被拒绝 | 立即写入失败结果文件，说明阻断点；尽量清理自己的锁目录 | ❌ 否（除非能绕开） |
| **临时目录创建失败** | 磁盘满、权限不足等导致无法创建临时工作区 | 立即写入失败结果文件（如可写），说明失败原因；无法写入则直接结束 | ❌ 否 |
| **编译失败** | 临时目录编译不通过 | 调试修复，无法修复则记录失败 | ✅ 是（除非触发高危 Bug） |
| **测试失败** | 单测运行不通过 | 分析原因，确认为缺陷则记录，继续优化 | ✅ 是（除非触发高危 Bug） |
| **锁竞争** | 获取共享经验库锁超时 | 记录警告，跳过经验写入，继续执行 | ✅ 是 |
| **文件 IO 异常** | 写入独立文件失败 | 按原子写文件契约处理，尽力重试 | ✅ 是（除非结果文件无法写入） |
| **配额中断** | 执行时间或资源超限 | 尽力清理自己的锁目录，尽量写入不完整结果，由 ut.md 兜底 | ⏹️ 中断 |
| **主项目源码变化** | 检测到主项目源码在执行中被修改 | 记录警告，继续执行，最终由 ut.md 统一验证 | ✅ 是 |

### 13.1 权限阻断详细处理

**前置说明**：
- 正常情况下，ut.md 已预先完成权限托管，不应出现权限阻断
- 如出现权限阻断，说明权限托管可能失效，需要重新运行 /helix:ut

**遇到权限阻断时的执行步骤**：

1. **立即停止**当前操作，不等待，不反复重试
2. **尽力写入**失败结果文件（如有权限）：
   - 状态标记为 `状态: 失败`
   - 明确说明阻断点和原因
   - 在结果文件中追加：`权限托管异常，请重新运行 /helix:ut`
3. **尽力清理**自己的临时资源（如有权限）：只清理自己创建的锁目录
4. **直接结束**，不尝试其他操作
5. **结果文件也无法写入时**：直接结束，由 ut.md 超时机制处理

**执行完以上步骤后，立即停止执行，不再进行任何其他操作。任务已完成（因权限阻断终止）。**
